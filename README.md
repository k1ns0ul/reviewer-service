# Reviewer Service

Сервис для управления командами, пользователями и pull request’ами.

## Особенности

- RESTful API для управления командами, пользователями и PR
- Автоматическое назначение ревьюверов с учётом инвариантов
- Массовая деактивация команды с безопасным переназначением открытых PR
- Простая статистика по системе через HTTP
- Интеграция с PostgreSQL
- Unit‑тесты и нагрузочное тестирование

## Требования

- Docker 20.10+
- Docker Compose 2.0+
- Go 1.22+
- Make (опционально, для удобства использования Makefile)

## Быстрый старт

1. Клонируйте репозиторий

```
git clone https://github.com/<your-username>/reviewer-service.git
cd reviewer-service
```

Или, если у вас установлен Make:

```
make dev
```

3. Проверьте статус сервисов

```
docker-compose ps
```

Или:

```
make service-status
```


4. Доступ к сервисам:
- HTTP API: `http://localhost:8080`
- PostgreSQL: `localhost:5433` (внутри docker‑сети — `postgres:5432`)

## Работа с API

### HTTP API

Базовые эндпоинты:

- `GET /health` — проверка живости сервиса
- `GET /stats` — агрегированная статистика по PR, пользователям и командам

Работа с командами:

- `POST /team/add` — создание новой команды и пользователей
- `GET /team/get?teamName={name}` — получение информации о конкретной команде
- `POST /team/deactivate` — массовая деактивация всех активных участников команды с безопасным переназначением их открытых PR

Работа с пользователями:

- `POST /users/setIsActive` — изменение активности пользователя
- `GET /users/getReview?userId={id}` — получение списка PR, где пользователь является ревьювером

Работа с PR:

- `POST /pullRequest/create` — создание нового PR и назначение ревьюверов
- `POST /pullRequest/merge` — мердж PR (идемпотентный, повторный вызов не ломает состояние)
- `POST /pullRequest/reassign` — переназначение ревьювера для открытого PR

## Метрики / статистика

Сервис предоставляет простой HTTP‑эндпоинт `/stats` со сводной статистикой:

- количество PR и смерженных PR
- количество назначений ревьюверов
- количество пользователей / активных пользователей
- количество команд

Эндпоинт можно опрашивать внешними системами мониторинга или использовать для ручной проверки состояния системы.

## Работа с базой данных

### Структура базы данных

База данных автоматически инициализируется при первом запуске, применяя миграции из директории `migrations`. Структура включает (упрощённо):

- `users` — таблица пользователей
- `teams` и `team_members` — таблицы команд и их участников
- `pull_requests` и связанные таблицы — PR, статусы, авторы и ревьюверы

### Подключение напрямую к БД

PostgreSQL доступен по адресу:

```
postgresql://postgres:postgres@localhost:5433/reviewer_service?sslmode=disable
```

## Тестирование

```
make test
```

Нагрузочное тестирование (Go‑бенчмарки):

```
go test ./tests/load -bench=. -run=^$ -benchtime=3s
```

Пример результата:

```
Benchmark_AllEndpoints-8 249 5123402 ns/op
```


Это соответствует средней задержке одного полного цикла по основным эндпоинтам порядка 5.1 ms и эквивалентной пропускной способности около 190–200 таких циклов в секунду на ядро при отсутствии ошибок.

## Вопросы / проблемы и решения


1. **Массовая деактивация и безопасное переназначение PR.**  
   Вместо одного большого `UPDATE` в БД выбрана поэтапная логика в сервисах:  
   `UserService.DeactivateTeamAndReassign` деактивирует только активных пользователей и для каждого из них вызывает `PRService.ReassignForDeactivatedReviewer`.  
   За счёт этого переиспользуется уже существующая логика выбора ревьюверов, а инварианты (не назначать автора, брать только активных из команды и тк далее) проверяюстя единообразно.

2. **Статистика и метрики.**  
   Изначально планировались Prometheus‑метрики, но просто нехватило времени на реализацию.  
   В итоге реализован простой эндпоинт `/stats`, который возвращает агрегированные значения напрямую из БД и полностью закрывает требование задачи.

3. **Нагрузочное тестирование.**  
   Попытки использовать внешние тулзы (vegeta) заняли много времени на настройку формата таргетов и не дали дополнительных плюсов относительно задания.  
   В итоге нагрузка оформлена как Go‑бенчмарк `Benchmark_AllEndpoints`, который:
   - параллельно дергает основные эндпоинты сервиса;
   - даёт измеримое `ns/op`.  
   Результат прогона и интерпретация вынесены в раздел “Нагрузочное тестирование” и показывают, что сервис укладывается в заданные ограничения по времени ответа и успешности.
